# T11 速度の変更（ピッチも変わる方式・ピッチを保つ方式）

ブランチ: `task/T11-tempo`（main から作成）
前提資料: `docs/research/R01-bpm-tempo-quality.md`（C 章）, T05 の `web/js/engine.js`・`player.js`, T10/T10c の拍と BPM, T04 のジョブ・ワーカー・配信用データ

## 目的（ユーザーの要望）
BPM 表示を使って曲の速度を変えられるようにする。「ピッチも変わってよい方式」と「ピッチを変えない方式」を選べる。全 stem の同期と、stem の即時切り替えは今までどおり保つ。
PC でスライダーを動かすとすぐ変わる方式（ブラウザ内の伸縮）は T11c で行う。このタスクでは作らない。

## 速度の指定
- 「速度」は倍率 r（例 0.50〜2.00）で持つ。画面では次の2通りで指定できる:
  - テンポのスライダー（DJ 風に ±8% / ±16% / ±50% の幅を切り替え）と、細かい ± ボタン（0.1%）。
  - 目標 BPM の入力（再生位置の区間の BPM を基準に r を計算）。
- 表示する BPM は「区間の BPM × r」。元の BPM も小さく出す。
- 「元の速度に戻す」ボタン。
- キー操作の案を報告（例: 速度 ± とリセット）。
- 曲ごとの速度と方式をブラウザに保存して、次に開いたときに戻す。

## 方式1: ピッチも変わる（playbackRate）
- 全 stem の AudioBufferSourceNode に同じ時刻で同じ playbackRate を設定する（R01 C-1）。
- 再生位置の計算を「基準の曲時刻 ＋ 経過時間 × r」に変え、速度を変えたときに基準を置き直す。シーク、一時停止、ループ（loopStart/loopEnd は曲時刻のまま）、キュー、拍の線、BPM 表示、stem 切り替えがすべて曲時刻で正しく動くこと。
- 速度を変える瞬間に stem 間がずれないこと（ブラウザテストで確認）。

## 方式2: ピッチを保つ（サーバーで作る）
- 指定した r で、各 stem の音声をサーバーで伸縮して配信用の音声（Opus）を作り、キャッシュする（R01 C-2 (b)）。
  - ffmpeg の rubberband フィルタを使う（導入済みの ffmpeg に入っている）。stem ごとに並列（CPU の論理コア数に応じた上限）。外部コマンドは `stemapp.proc` の決まりで起動。
  - 入力は master の FLAC、出力は stream と同じ形式・ビットレート。
  - 伸縮後の長さがどの stem でも同じになることを確認し、差があれば切りそろえる。
  - 作る処理はワーカーのジョブとして1件ずつ実行（GPU は使わない。分割ジョブより後回しでよい）。進捗は SSE で配信（T04 の仕組みを再利用）。キャンセルできる。
- 置き場所: `data/cache/tempo/<job_id>/<r を小数3桁>/`（例 `cache/tempo/12/1.100/`）。stem の保存フォルダ（T13 で構成が変わる予定）には置かない。DB に記録（STEM_RENDITION に purpose=`tempo` と倍率の列を足すか、専用の表を作る。判断して報告し、ER.md を更新）。
- キャッシュの上限: 1曲あたり倍率3つまで、全体で 2GB（設定で変更可）。超えたら最も長く使っていないものから消す。曲やジョブを削除したら一緒に消す。
- 画面の流れ: ピッチを保つ方式で速度を変えると、作っている間は「作成中 xx%」を出し、**その間は方式1（ピッチも変わる）で指定の速度で鳴らしておく**か、元の速度のまま鳴らすかを選べる（既定は元の速度のまま。ユーザーの好みが分からないので報告時に両方の聞こえ方を書く）。できたら、同じ曲時刻の位置からシームレスに差し替える（stem の選択とループは保つ）。
- すでにある倍率を選んだら即座に切り替える。
- 伸縮後の音声の波形は、元の peaks を時間軸だけ伸縮して描く（新しい peaks は作らなくてよい）。

## 共通
- 拍・キュー・ループはすべて元の曲の時刻で持つ（保存データは変えない）。
- 速度を変えても、stem の ON/OFF の即時切り替えは今までどおり効く。
- iPhone（T06）でも方式1・方式2の両方が使える作りにする（ブラウザ内だけで完結する重い処理を入れない）。

## テスト
- 位置の計算の純粋関数（速度変更、シーク、ループの折り返し）。
- 伸縮ジョブ（Fake の伸縮器と、`@pytest.mark.ffmpeg` で本物の rubberband）: 長さ、stem 間の長さ一致、キャッシュの上限と削除、キャンセル、曲の削除で消える。
- API。
- ブラウザテスト: 方式1で速度を変えても stem の GainNode・位置が正しく、再生が止まらない。方式2で作成 → 差し替え（Fake）。スクリーンショット（PC・スマホ幅）。

## 実機での確認
- 実データの曲（ユーザーの曲。例「春嵐」）を一時データフォルダにコピーして、方式2で r=0.9 と 1.1 を作り、処理時間とキャッシュの容量を報告する。stem 間のずれ（相互相関などで ms 単位）を測って報告する。
- ユーザーの実データを書き換えない。
