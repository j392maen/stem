# T10 拍・小節の解析と表示

ブランチ: `task/T10-beats`（main から作成）
前提資料: `docs/research/R01-bpm-tempo-quality.md`（A・B・E 章）, `docs/SPEC.md`, `docs/ER.md`, T04 の後処理（`delivery.py`、`jobs/`）, T05 の画面（`src/stemapp/web/js/waveform.js`, `player.js`）

## 目的
分割後に曲の拍と小節の頭（ダウンビート）を自動で求めて保存し、波形の上に拍の線・小節線を描き、再生位置の BPM を表示する。途中でテンポが変わる曲にも対応する。
手動補正の UI（1小節目をここに、×2/÷2、タップ、キューから計算）は次のタスク T10c、速度変更は T11 で行う。ただし、データの持ち方は補正（アンカー）を後から足せる形にしておく。

## ユーザーが承認したこと
- beat_this（CPJKU、MIT）と torchaudio 2.11（cu128）の導入、重み（約 78MB）のダウンロード。

## 作るもの

### 1. 依存
- optional `gpu` に `beat-this` と `torchaudio`（Windows は cu128 index。torch と版をそろえる）を足す。`uv.lock` を更新。
- 重みは `models_dir`（`data/models/beat_this/` など）に置く。beat_this が既定で使うキャッシュ先（ユーザーのホーム）に置かれる場合は、置き場を設定で変えられるか調べ、できなければ報告。
- beat_this の import は解析器のモジュールの中だけにする（GPU 依存が無い環境でも他が動くように。T02 の AudioSeparatorBackend と同じ考え方）。

### 2. 解析器 `src/stemapp/beats/`
- `BeatAnalyzer` プロトコル: 音声（44.1kHz ステレオ float32、または normalized.wav のパス）を受け取り、拍の時刻の列と、ダウンビートの時刻の列を返す。
- `BeatThisAnalyzer`: beat_this で解析（GPU があれば GPU、無ければ CPU）。DBN（テンポ固定の後処理）は使わない。入力は元の曲（normalized.wav）。
- `FakeBeatAnalyzer`: テスト用。指定した BPM（区間ごとに変えられる）と拍子で規則的な拍を返す。
- 解析結果から、**区間ごとの BPM**（拍の間隔から求め、細かいゆれは中央値などでならし、テンポが変わったところで区切る）と**拍子の推定**（ダウンビートの間の拍数の最頻値）を計算する純粋関数を作る。区切り方の閾値は定数にして、根拠をコメントに書く。

### 3. データ（ER の追加。`docs/ER.md` も更新）
- `BEAT_GRID`（曲ごと、track_id PK FK）: analyzer（名前と版）, beats_json（秒の配列）, downbeats_json, time_signature（推定の拍子。例 4）, created_at。
- `BEAT_ANCHOR`（T10c で使う。今回は表だけ作ってよい）: anchor_id PK, track_id FK, position_sec, kind（downbeat / beat）, bar_number（任意）, bpm（任意）, created_at。
- DB の移行は T04 の `migrate_db` の方式（無ければ作る）。

### 4. 実行のタイミング
- 分割ジョブの後処理（配信用データ作成の後）に「拍を解析中」の段階を足す。子プロセスの中で行う。解析に失敗してもジョブは failed にせず、警告をログと画面用の項目に残す（拍が無くても再生はできるため）。
- 既に分割済みの曲のために、T05 の「配信用データの作り直し」（`POST /api/jobs/{id}/postprocess`）で拍が無ければ拍も作る。加えて `POST /api/tracks/{id}/beats`（再解析）と CLI `stemapp beats <track_id> [--force]` を作る。

### 5. API
- `GET /api/tracks/{id}/beats`: beats, downbeats, time_signature, segments（開始秒・終了秒・BPM の配列）, analyzer。まだ無ければ 404（画面は1秒目盛りのまま）。

### 6. 画面
- 拡大波形の目盛りを、拍の線（細く暗め）と小節線（やや太く明るめ、小節番号を小さく表示）に置き換える。拍が無い曲は今の1秒目盛りのまま。
- 概観波形には小節線を間引いて描く（例: 8 または 16 小節ごと。表示幅に応じて）。
- 再生位置の BPM を再生ボタンの近くに表示（小数1桁。例「128.0 BPM」）。区間が変わると表示も変わる。拍子も小さく表示（例「4/4」）。
- 線の色はユーザーの好み（暗い DJ 風、差し色は赤系統）を守り、stem の波形より目立たせない。差し色の赤は再生位置の線と紛れるので小節線には使わない。

### 7. テスト
- 区間 BPM・拍子の計算（一定テンポ、途中で 120→140 に変わる、小さなゆれ、拍の抜け・倍取りに近い入力）。
- Fake 解析器での後処理の流れ、失敗してもジョブが done のままになること、API、移行。
- GPU テスト（`@pytest.mark.gpu`）: 120 BPM のクリック音（合成）を beat_this で解析し、区間 BPM が 120±1 になる。途中で 120→150 に変わる合成音で区間が2つに分かれる。
- ブラウザテスト（`-m browser`）: 拍のある曲で小節線が描かれ、BPM 表示が再生位置で変わる（Fake 解析器、テンポ変化あり）。スクリーンショットを撮る。

## 実機での確認（完了条件に含む）
- 既存の曲（`synth_4min` など）に `stemapp beats` をかけ、結果（区間 BPM、拍子、処理時間、GPU/CPU）を報告する。
- テンポが途中で変わる合成曲（例: 120 BPM を 30 秒 → 140 BPM を 30 秒、ドラム風の音）を作って取り込み・分割（fast）し、画面で小節線と BPM 表示が切り替わるのを Playwright（Edge）で撮る。確認用の曲は最後に削除。

## 注意
- ユーザーの `stemapp serve`（ポート 8000）が動いていると `uv sync` が「ファイルが使用中」で失敗する。依存の追加が必要な段階で失敗したら、サーバーを止めずに作業を止め、監督役に「サーバーを止めてもらう必要がある」と報告して待つ（監督役がユーザーに頼む）。依存の追加が不要な作業から先に進めてよい。
- 同時に別の担当が T12（分離の見直し）を別フォルダ（git worktree）で進めており、GPU を使うことがある。GPU テストが VRAM 不足で失敗したら、nvidia-smi で他のプロセスを確かめ、時間をおいて再実行する。
- 外部コマンドの起動は `stemapp.proc` の決まりに従う。
