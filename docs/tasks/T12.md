# T12 分離品質の見直し（聴き比べの仕組みと候補の用意）

ブランチ: `task/T12-separation-quality`（main から作成）
前提資料: `docs/research/R01-bpm-tempo-quality.md`（D 章・E 章）, `docs/SPEC.md` 5章, T02 の `src/stemapp/separation/`, `src/stemapp/seed.py`, T05 の画面

## 目的
ユーザーの聴いた感想「サブボーカルが他の stem に残る」「メインに入るべきものがサブに入る」「その他に多く入りすぎ」を改善するため、候補となる分け方を複数用意し、**同じ曲を複数の分け方で分割して、アプリの画面で切り替えて聴き比べられる**ようにする。どれを既定にするかは、ユーザーが聴いて決める（このタスクでは既定を変えない）。

## ユーザーが承認したこと
- karaoke モデル `bs_roformer_karaoke_anvuew.ckpt`（GPL-3.0）と gabox 系 karaoke（`mel_band_roformer_karaoke_gabox.ckpt`、v2 があれば v2 も）のダウンロード。
- これ以外のモデルのダウンロードは、必要なら理由とサイズを報告して監督役の判断を待つ。

## 作るもの

### 1. パイプラインの選択肢（プリセットの options や PRESET_STEP で指定。コードに直書きしない）
- **残差の行き先**（R01 D-1）: 今は「元の曲 − 上位 stem の合計」を other に足している。これを選べるようにする:
  - `other`（今のまま）
  - `vocals`: 残差を vocals 側に足す（ボーカルの平均で生じた差をボーカルに戻す）。その後の lead/backing の計算は、足した後の vocals を使う。
  - `split`: 残差を「vocals のアンサンブルで生じた差」と「それ以外」に分け、前者を vocals、後者を other に足す。できるなら。難しければ理由を報告して省く。
  - どの方式でも「上位 stem の合計＝元の曲」「lead＋backing＝vocals」は必ず守る（テストで確認）。
- **karaoke の入力**: PRESET_STEP の input に `mixture` を使えるようにする（今は vocals）。mixture に karaoke をかけた場合、lead ＝ karaoke の Vocals 出力、backing ＝ vocals − lead。
- karaoke の複数モデルの平均（既存の ensemble_weight）。

### 2. 聴き比べ用のプリセット（seed で追加。ユーザー向けの fast / standard / best とは別に「実験」として区別できる印を付ける）
少なくとも次を用意する（名前は日本語の短い説明を付ける）:
- `exp_resid_vocals`: standard ＋ 残差を vocals へ
- `exp_kara_mix`: standard ＋ karaoke を元の曲にかける
- `exp_kara_anvuew`: standard の karaoke を anvuew ＋ frazer の平均に
- `exp_combo`: 残差を vocals へ ＋ karaoke（anvuew ＋ frazer）を元の曲にかける
- 必要と判断した組み合わせがあれば追加してよい（理由を報告）。

### 3. 同じ曲の複数の分け方を画面で切り替える
- 同じ曲に、プリセットの違う done のジョブを複数持てるようにする（今は「分割済みなら force が要る」。プリセットが違えば force なしで登録できるようにするか、画面から明示的に「別の分け方で分割」を選べるようにする）。
- プレイヤーに「分け方」の切り替え（ジョブの選択）を付ける。切り替えると、再生位置と stem の選択をなるべく保ったまま、そのジョブの stem に入れ替える。
- ライブラリの取り込み・分割の品質の選択肢に、実験プリセットを「実験」として区別して出す（通常は隠し、切り替えで出す程度でよい）。
- 曲の削除・ジョブの扱い（T04）と矛盾しないこと。ジョブ単位の削除 `DELETE /api/jobs/{id}`（実行中は 409）も作る。

### 4. 数値での比較（参考）
- 聴き比べの補助として、ジョブごとに stem ごとの RMS（dB）と「補正前の残差」（T02）を記録・表示する（API に含め、プレイヤーの分け方の切り替えの近くに小さく出す程度）。

### 5. テスト
- 残差の行き先ごとの合計一致（Fake）、karaoke を mixture にかけたときの lead/backing の関係、プリセットの検証（不正な組み合わせを弾く）。
- 同じ曲に複数ジョブ、ジョブの削除、API、画面でのジョブ切り替え（`-m browser`、Fake）。
- GPU テストは既存のものが通ること。

## 実機での確認（完了条件に含む）
- モデルのダウンロード（anvuew、gabox）。サイズを報告。
- 手元の曲がユーザーのライブラリにあれば、その1曲（最新で分割済みの、合成音でない曲。無ければ `synth_4min`）に、実験プリセットをすべてかけ、処理時間と GPU メモリ最大を表にする。**ユーザーの曲の既存ジョブは消さない**。作ったジョブは聴き比べのために残す（合成音の場合は消してよい）。
- Playwright（Edge）でプレイヤーの分け方の切り替えを操作してスクリーンショットを撮る。

## 注意
- このタスクは git worktree（別フォルダ）で作業する。依存（Python パッケージ）は足さない。テストや実行は main の `.venv` の python（`C:\mine\stem\.venv\Scripts\python.exe`）と `PYTHONPATH=<worktree>\src` で行い、データは `STEMAPP_DATA_DIR` を指定しない限り実データ（`C:\mine\stem\data`）になることに注意する。実機の分割はユーザーのデータで行ってよいが、既存の曲やジョブを消さない。
- 同時に別の担当が T10（拍の解析）を main フォルダで進めていて、GPU を使うことがある。VRAM 不足で失敗したら時間をおいて再実行する。
- ユーザーの `stemapp serve`（ポート 8000）が動いていても止めない。確認用のサーバーは別ポート。実データ DB を別のサーバーが同時に使うことになるので、ワーカーの二重起動防止（`data/worker.lock`）に注意し、確認用サーバーはワーカーを動かせない場合がある。その場合の実機確認の方法を工夫し、報告する（例: 一時データフォルダにモデルをジャンクションで共有し、曲をコピーして取り込む）。
- 外部コマンドの起動は `stemapp.proc` の決まりに従う。
