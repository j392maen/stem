# T04 ジョブと API

ブランチ: `task/T04-jobs-api`（main から作成）
前提資料: `docs/SPEC.md`（7章・8章）, `docs/ER.md`, `docs/PLAN.md` の「持ち越し事項」, T01〜T03 の `src/stemapp/`

## 目的
ブラウザ（T05）と iPhone（T06）から使うためのサーバー側を作る。取り込み・分割をバックグラウンドで動かし、進捗を配信し、キャンセルでき、分割後に配信用の音声と波形データを作り、REST API で全部取り出せるようにする。
画面（HTML/JS）はまだ作らない。

## 監督役が決めたこと（このとおりに作る）
- **ワーカー**: 分割は Web サーバーとは別のプロセスで動かす。ワーカーは DB の queued ジョブを古い順に1件ずつ実行する（GPU は同時に1ジョブ）。1ジョブごとに子プロセスを起動して分割させ、キャンセル時はその子プロセスを終了させる（GPU メモリを確実に解放するため）。`stemapp serve` はワーカーも一緒に起動し、サーバー終了時に止める。`stemapp worker` で単独起動もできる。
- **起動時の片付け**: ワーカー起動時に status=running のまま残ったジョブを failed（error_message「中断されました（アプリの再起動）」）にし、途中の `data/stems/<job_id>` を消す。Ctrl+C（KeyboardInterrupt）でも同じ後始末をする。
- **キャンセル**: queued は即 canceled。running は SEPARATION_JOB に追加する `cancel_requested`（bool）を立て、ワーカーが検知して子プロセスを終了 → canceled にして stems フォルダを消す。検知は1秒以内の間隔で。
- **音量の上限（T02 持ち越し）**: 分割結果を保存する前に、mixture と全 stem の最大絶対値を調べる。1.0 を超えていたら、全 stem に同じ倍率（0.999 / 最大値）をかける。倍率は SEPARATION_JOB に追加する `output_gain_db`（float、既定 0.0）に記録する。これで stem 同士のバランスと「足すと mixture × 倍率」の関係が保たれる。T02 の「±1 で切り詰め」は、この処理の後の安全策として残してよい。
- **DB の列追加**: 既に実データの DB があるので、`init_db()` に簡単な移行処理を入れる（テーブルにその列が無ければ `ALTER TABLE ... ADD COLUMN`）。Alembic は入れない。`docs/ER.md` の SEPARATION_JOB 行にも追加した2列を書き足す。
- **配信用の音声（stream rendition）**: 各 stem から Opus 128kbps を ffmpeg で作り、`data/stems/<job_id>/stream/<code>.webm` に置く。STEM_RENDITION（purpose=stream, codec=opus, bitrate_kbps=128）に登録する。作成処理はコーデック・コンテナを引数で変えられるようにする（iPhone の実機確認は T06 で行い、必要なら AAC を追加する）。
- **波形 peaks**: 各 stem について、samples_per_px = 256, 1024, 4096, 16384 の4段階を作る。1ピクセルごとに左右をまとめたモノラルの min と max を int8（-127〜127）で持つ。ファイル形式は「小さなヘッダ（マジック `STPK`、版、samples_per_px、サンプルレート、点の数）＋ min,max の並び」のバイナリにし、形式を `docs/PEAKS.md` に書く。WAVEFORM に登録する。
- **後処理の位置**: Opus と peaks の作成は分割ジョブの最後の段階（stage「配信用データを作成中」）として同じ子プロセスで行う。失敗したらジョブを failed にする。
- **パスコード**: 設定 `passcode` が空なら認証なし。設定されていれば `POST /api/login`（パスコード）で署名付き Cookie（HttpOnly、SameSite=Lax、有効期限30日）を発行し、`/api/health` と `/api/login` 以外の `/api/*` は Cookie が無いと 401。パスコードの比較は `hmac.compare_digest`。署名用の秘密鍵は初回起動時にランダムに作って `data/secret.key` に保存する。ログインの連続失敗は、同じ接続元で1分に5回までに制限する。
- **host の警告（T01 持ち越し）**: `doctor` に「待ち受けアドレス」の項目を足し、host が 127.0.0.1 / localhost / ::1 以外なら「注意」（外部に公開される可能性がある、Tailscale Serve を使う想定）を出す。
- **同時取り込み（T03 持ち越し）**: import_file で audio_hash の一意制約違反（IntegrityError）が起きたら、探し直して「既存」として返す。
- httpx の非推奨警告はそのままにする。

## 作るもの

### 1. ジョブ
- `src/stemapp/jobs/`: ジョブの登録（enqueue）、ワーカー本体、子プロセスの起動と監視、キャンセル、起動時の片付け。
- 子プロセスには job_id だけを渡し、子プロセスが DB から読んで T02 の `separate_track` を実行する（進捗は T02 のコールバックで JOB に書く）。
- テストでは FakeSeparator を使う子プロセス（または子プロセスを使わない同期実行モード）で動かせるようにする。子プロセスを実際に起動して終了させるテストも1つは入れる（Fake で、Windows でも動くこと）。

### 2. 取り込みの非同期化
- URL の取得は時間がかかるので、API からはバックグラウンド（サーバー内のスレッド）で実行する。INPUT_SOURCE の fetch_status を `queued` → `fetching` → `done` / `failed` と更新する。T03 の import_file / fetch_url を使う（二重実装しない）。そのために T03 の関数を「INPUT_SOURCE を先に作ってから取得する」形に直す必要があれば直してよい。
- 取り込みの依頼時に `separate: true` と `preset` を指定すると、取り込み完了後にそのまま分割ジョブを登録する。既に分割済みの曲なら登録しない（`force` で登録）。

### 3. REST API（`/api` 以下、JSON。日本語のエラーメッセージを `{"detail": "..."}` で返す）
- 認証: `POST /api/login`, `POST /api/logout`, `GET /api/me`（ログイン状態）
- 取り込み: `POST /api/imports`（multipart のファイル、または JSON の url。任意で separate, preset, force）→ source_id を返す。`GET /api/imports/{source_id}`（状態、理由コード、日本語メッセージ、track_id）
- 曲: `GET /api/tracks`（一覧。タイトル、アーティスト、長さ、最新ジョブの状態）、`GET /api/tracks/{id}`（詳細、ジョブ一覧）、`DELETE /api/tracks/{id}`（DB と `tracks/<id>`・関連する `stems/<job_id>` を消す。実行中のジョブがあれば 409）
- ジョブ: `POST /api/tracks/{id}/jobs`（preset, force）、`GET /api/jobs/{id}`、`POST /api/jobs/{id}/cancel`、`GET /api/jobs/{id}/events`（Server-Sent Events。progress・stage・status が変わるたびに送る。終わったら閉じる）
- stem: `GET /api/jobs/{id}/stems`（stem ごとに種類 code、表示名、色、親、is_residual、rms_db、is_silent、rendition の URL と bytes、peaks の URL）
- ファイル配信: `GET /api/files/renditions/{rendition_id}`、`GET /api/files/peaks/{stem_id}/{samples_per_px}`。音声は HTTP Range（部分取得）に対応する（iPhone の再生に必要）。data フォルダの外は絶対に返さない。
- マスタ: `GET /api/stem-types`, `GET /api/stem-groups`, `GET /api/listen-presets`, `GET /api/presets`（分割プリセット。名前と既定）

### 4. テスト
- ジョブ: 登録→実行→done、進捗の更新、失敗→failed、queued のキャンセル、running のキャンセル（子プロセスが止まり、canceled、フォルダが消える）、起動時の片付け、1件ずつ順番に実行される。
- 音量の上限: ±1 を超える mixture で倍率がかかり、output_gain_db が記録され、stem の合計が mixture × 倍率に一致する。
- 移行: 列の無い古い DB に init_db をかけると列が足され、既存の行が残る。
- Opus と peaks（`@pytest.mark.ffmpeg`）: rendition と WAVEFORM が登録され、peaks ファイルのヘッダと点の数が正しく、min ≤ max。
- API: 全エンドポイントの正常系と主な異常系（404、409、401、Range の 206 と Content-Range、data フォルダ外へのパス）。パスコードあり・なしの両方。ログインの回数制限。
- 取り込み API: ファイル取り込み、URL 取り込み（Fake の yt-dlp）、separate=true でジョブが登録される。
- ネットワークに出るテストは作らない。

## 実機での確認（完了条件に含む）
- `uv run stemapp serve`（ワーカー込み）を起動し、API だけを使って次を行う（curl か Python のスクリプトで）:
  1. 30秒ほどの音声ファイル（合成音でよい）を `POST /api/imports` で separate=true, preset=fast で送る
  2. `/api/jobs/{id}/events` で進捗が流れ、done になる
  3. `/api/jobs/{id}/stems` から stream rendition を Range 付きで取得でき、peaks も取得できる
  4. もう1件登録して running 中にキャンセルし、canceled になって GPU メモリが解放される（nvidia-smi で確認）
  5. passcode を設定した状態で、ログイン前は 401、ログイン後は取得できる
- 確認の後、サーバーとワーカーのプロセスを必ず止める。実データの DB を使ってよいが、確認用に作った曲は最後に `DELETE /api/tracks/{id}` で消す。

## 注意
- `uv run` が「ファイルが使用中」で失敗する場合、ユーザーの `stemapp serve` が動いている可能性がある。そのサーバーは止めず、`uv run --no-sync` を使い、報告に書く。ポート 8000 が使用中なら、確認用のサーバーは別のポート（例 8001）で起動する。
- 依存を足す場合（例: 署名 Cookie 用の itsdangerous）は最小限にし、報告に書く。
